### 关于「代码规模」

原始对比表写的是「768 → ~500，-35%」，**这个数字不准确**。

实际统计（`wc -l`）：

```
R01: 768 行，分布在 3 个几乎相同的文件里，其中约 650 行是重复的
R02: 1097 行实现（src 691 + scenarios 406） + 314 行测试
```

**行数没有减少，反而增加了。** 但这不是退步：
R01 的 768 行里真正独立的逻辑很少，改一处 bug 要在三个文件里同步改；
R02 把重复收敛为单一实现，多出来的行数是**抽象层次与测试**的成本。
衡量重构质量应该看「重复消除」「可测试性」「缺陷可定位性」，而不是行数增减。

## 本次补充修复（2026-09-15）

在整理本仓库时，发现三个 R01/R02 遗留问题，已一并修复：

| # | 问题 | 根因 | 修复 |
|---|------|------|------|
| 1 | `summary.json` 的 `lane_invasion_events` 高达 1410/1619（87%），指标失真 | 回调把 `lane_invasion_flag` 置 True 后**从不复位**，主循环每 tick 都计入 | 新增 `reset_lane_invasion_flag()`，读后即复位 |
| 2 | `config/default.yaml` 的 `cooldown_seconds` **从未生效** | 代码里写死为类常量（避障 5.0，与 YAML 的 3.0 不一致） | 改为构造参数并读取 YAML；**YAML 对齐 5.0**（该值才是产出「4 次/35s」的真实值） |
| 3 | 同一份 config 两次运行结果不一致（一次 3 次碰撞 FAIL，一次 35s PASS） | `spawn_index: null` 时走 `random.choice`，全程无 `random.seed()` | `runtime.seed: 42` + `setup_ego()` 中播种 |

### 修复后的实测验证（2026-09-15，重启 CARLA server 重跑）

环境：CARLA 0.9.11 · **Town03** · 静态障碍物场景 · `seed=42`

> 顺带确认了一处此前的疑问：实际加载的地图是 **Town03**，
> 而非上游 `config.yaml` 里声明的 `Town05` —— 上游的 config 被忽略，
> 代码中的硬编码坐标系（Town03 专用）才是实际生效的那个。

**修复 1：`lane_invasion_events` 指标**

| 数据文件 | 结果 | `lane_invasion_events` |
|---|---|---|
| `20260810_214906`（修复前·静态） | PASS | **1410** ← 失真值 |
| `20260810_215153`（修复前·动态） | PASS | **1205** ← 失真值 |
| `20260915_130415`（修复后） | FAIL | **9** |
| `20260915_130503`（修复后） | FAIL | **9** |

从 1410 降到 9，与「标志位读后复位」的预期一致。
剩余的 9 次是真实事件（运行日志中可见多次 `穿越车道!` 提示）。

**修复 3：可复现性（受控对比）**

用同一段落点选择逻辑连续试验 3 次：

| 条件 | 3 次选中的生成点索引 | 落点 |
|---|---|---|
| 有种子（`seed=42`，修复后） | 57, 57, 57 | x=-74.62, y=-95.05（**完全一致**） |
| 无种子（修复前） | 12, 140, 125 | 每次都不同 |

两次修复后运行的首帧 x 坐标均为 `-74.62`，与种子选中的落点吻合，证明种子生效。

**修复 2：冷却配置生效（受控实验）**

临时把 `avoidance.cooldown_seconds` 从 5.0 改为 30.0 后重跑：

| 冷却值 | 避障触发 | 结果 |
|---|---|---|
| 5.0（仓库默认） | 3 次，间隔 5.25 s / 5.48 s | FAIL，3 次碰撞 |
| 30.0（临时实验值） | **1 次**（后续被冷却挡住） | PASS，0 碰撞 |

改 YAML 值即改变行为，证明配置确实被读取 —— 修复前它是写死的类常量，改 YAML 完全无效。

> 该实验的数据未保留：其配置与仓库中的 `default.yaml` 不一致，
> 留在仓库中会造成「同样配置为何结果不同」的困惑。

### 一处仍未解决的差异

修复 3 只固定了**落点**，没有让仿真本身**逐步确定**：

| 指标 | 运行 1 | 运行 2 |
|---|---|---|
| 结果 / 碰撞数 | FAIL / 3 | FAIL / 3 |
| `lane_invasion_events` | 9 | 9 |
| `avoidance_ticks` | 505 | 507 |
| `total_ticks` | 1225 | 1245 |

判定结果一致，但 tick 数有约 1.6% 的浮动。原因是控制循环**按墙钟时间推进**
（`time.sleep(tick_rate)`），场景以「运行 30 秒」为界而非「运行 N 步」为界，
系统负载会影响实际步数。

**结论：落点已可复现、结果判定一致，但逐帧数据仍非完全确定。**
要彻底确定需改用 CARLA 的同步模式（`world.tick()` 显式推进），属后续可做的事。
